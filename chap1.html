Evolution of System Architecture

Stage 1

Single Server Setup

Everything runs on one server: web app, database, and cache. Simple, but fragile.

User → DNS → IP ↓ Web Server ├── Database └── Cache

Request flow: DNS lookup → HTTP request → HTML or JSON response.

Stage 2

Separate Web & DB Servers

Web and database tiers are split. Load balancer distributes traffic across multiple web servers.

User → Load Balancer ├── Web Server 1 └── Web Server 2 ↓ Master DB (writes) Slave DBs (reads)
1
User accesses via domain name (e.g., api.mysite.com)
2
DNS returns IP address to browser or mobile app
3
HTTP request is sent to the web server
4
Web server returns HTML pages or JSON API responses
🗄️

Database Selection

Relational — SQL

Structured & Proven

MySQL, PostgreSQL, Oracle. Store data in tables and rows. Support JOIN operations. 40+ years of battle-tested usage.

MySQL PostgreSQL Oracle
Non-Relational — NoSQL

Flexible & Scalable

CouchDB, Cassandra, DynamoDB, Neo4j. Four types: key-value, graph, column, and document stores.

Key-Value Graph Column Document
When to choose NoSQL: Super-low latency requirements, unstructured or non-relational data, serialization-only needs (JSON, XML, YAML), or storing truly massive datasets.

⚡

Load Balancer

Evenly distributes incoming traffic across web servers. Uses private IPs between itself and web servers for security.

[Public IP] User ──────→ Load Balancer / \ [Private IP] [Private IP] Web Server 1 Web Server 2
Benefit

No Single Point of Failure

If Server 1 goes down, all traffic is automatically routed to Server 2.

Benefit

Auto-Scaling

Add new servers anytime — the load balancer routes to them automatically.

🔄

Database Replication

Based on the master/slave model. Writes go to master; reads are distributed across slave replicas.

Writes only Client ──────→ Master DB │ async replication ┌─────────┼─────────┐ ▼ ▼ ▼ Slave 1 Slave 2 Slave 3 (reads) (reads) (reads)
BenefitDescription
PerformanceWrites on master only; reads distributed across slaves
ReliabilityData preserved even if one server is destroyed
High AvailabilityWebsite stays up even if a DB node goes offline
Failure handling: If the master goes offline, a slave is promoted to master — though data recovery scripts may be needed for sync gaps.
🚀

Caching

A temporary storage layer for expensive or frequently accessed data. Uses a read-through strategy.

Web Server │ ├── Check Cache ──(hit)──→ Return to Client │ │ │ (miss) │ ▼ └── Query DB → Store in Cache → Return to Client
ConsiderationDetails
When to useData read frequently, modified infrequently
ExpirationBalance — too short overloads DB, too long gives stale data
ConsistencyKeeping cache and DB in sync across regions is hard
Eviction PolicyLRU (most popular), LFU, FIFO
⚠️ Warning: Cache is volatile — never store critical persistent data exclusively in cache!
🌐

Content Delivery Network (CDN)

A geographically dispersed network that serves static content (JS, CSS, images, videos) from the edge server closest to the user.

1
User requests image.png via CDN URL
2
CDN checks its edge cache; if miss, fetches from origin server
3
Origin returns the file with an optional TTL header
4
CDN caches and returns to user; subsequent requests are served from cache
File Invalidation: Use CDN API or URL versioning (image.png?v=2) to bust stale caches.
🔗

Stateless Web Tier

Move session state out of web servers into persistent shared storage (Redis, NoSQL).

❌ Stateful (Bad)

Sticky Sessions

User A must always hit Server 1 because that's where their session lives. Hard to scale, single point of failure.

User A → Server 1 (session here) User B → Server 2 (session here)
✅ Stateless (Good)

Shared State Store

Any web server can handle any user. Sessions live in a shared data store like Redis.

User A → Any Server → Redis User B → Any Server → Redis
🌍

Data Centers

GeoDNS routes users to the nearest data center. On failure, 100% traffic is rerouted to the healthy DC.

geoDNS ├── US-East Data Center (x% traffic) └── US-West Data Center ((100-x)% traffic)
ChallengeSolution
Traffic redirectionGeoDNS routes users to nearest data center
Data synchronizationAsync multi-DC replication
Test & deploymentAutomated deployment tools for consistency
📨

Message Queue

A durable, in-memory component for asynchronous communication. Producers and consumers are decoupled and scaled independently.

Producer (web servers) ↓ [Message Queue] ↓ Consumer / Workers
Use Case

Photo Processing Pipeline

Web Server pushes jobs to queue. Photo Workers pull and process independently. Either side can scale or restart without breaking the other.

Advantage

Loose Coupling

System remains available even if one side is temporarily down. Producers and consumers scale independently based on load.

🗃️

Database Scaling

Vertical

Scale Up

Add more CPU/RAM/Disk. AWS RDS offers up to 24 TB RAM servers. Limited by hardware ceiling and cost. Still a single point of failure.

Horizontal

Sharding

Split DB into smaller shards — same schema, different rows. A sharding key like user_id determines which shard stores which data.

user_id % 4 → 0 → Shard 0 1 → Shard 1 2 → Shard 2 3 → Shard 3
Sharding ChallengeDescription
ReshardingWhen a shard runs out of space; use consistent hashing
Celebrity ProblemHot shard overloaded by famous users; allocate dedicated shard
Join & De-normalizationCross-shard JOINs are hard; de-normalize tables as a workaround
✅

Summary: How to Scale to Millions

  • ✓Keep the web tier stateless
  • ✓Build redundancy at every tier
  • ✓Cache data as aggressively as possible
  • ✓Support multiple data centers
  • ✓Host static assets in a CDN
  • ✓Scale data tier by sharding
  • ✓Split tiers into individual services
  • ✓Monitor system and automate deployments
